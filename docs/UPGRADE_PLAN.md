## 2. ELEGNT 论文与当前算法的准确关系

原始资料：[Apple 项目页](https://machinelearning.apple.com/research/elegnt-expressive-functional-movement)、[论文全文](https://arxiv.org/html/2501.12493v1)。

论文 3.2.1 提出功能与表达的联合目标 `max F(trajectory) + gamma * E(trajectory)`。3.2.3 讨论动作原语。4.2 明确说明用户研究视频使用研究人员和动画设计师迭代设计的预录运动轨迹，经 WidowX 控制器执行。3.3 与 Photograph Light 场景描述响应指向手势调整灯位，以及关节扭矩感知/柔顺交互；并未提供足够细节来复现完整视觉手势识别器、连续手部跟随控制器或自动学习策略。

因此不能把视频的自然表现等同于已公开的端到端自主算法，也不能把当前代码称为苹果原版实现。

我们的实现位于 `lampkit/motion/generator.py`：

1. Policy 产生意图，如 `celebrate`，并指定目标、表达维度和优先级。
2. 依据本次观测到的人脸位置、提示区域或固定工作区，通过 look-at IK 求目标关节角。
3. 枚举纯功能动作、不同幅度的原语，以及原语组合；比较是否让灯头先动。
4. 用 minimum-jerk 插值构建轨迹；评分 `F + gamma * E`。
5. F 衡量目标、时长、角度变化和速度代理；E 来自人工填写的表达标签，不是学习出来的人类评价。
6. 选择得分最高的计划，用弹簧式平滑器逐帧播放，经 UDP 给 Blender，lab 展示同一份输出。

这比固定播放整段动画多了在线求目标与搜索，但仍是在人工定义的候选空间内选择。当前一个计划生成后通常播放到结束或被更高优先级计划替换，不会持续追随正在移动的手。现在的 reach/effort/noise 分数也不是接触力、真实电机噪声或碰撞验证。

升级目标：连续目标更新 → 约束轨迹规划 → 每个短周期重新计算剩余路径。表达动作只能叠加在完成任务和避免干扰的可行范围内。

## 3. 视觉模型如何分工

- **快速几何层：** 当前 MediaPipe Face Landmarker 提取脸部关键点、表情系数和变换矩阵。它不是我们的“困惑/不想学习分类器”。[官方说明](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)
- **手部几何层（待接入）：** 手部关键点＋桌面区域＋手相对灯头的位置。首轮先验证手掌定位、跟踪丢失、手势开始/结束，不直接把任何挥手当命令。
- **慢速语义层（待验证）：** FastVLM 可作为视觉问答/场景线索来源，而不是让它直接控制电机。[官方仓库](https://github.com/apple-aiml-research/ml-fastvlm)
- **融合层：** 加入来源、时间、新鲜度、质量、用户指令；表达“未知”和相互冲突，避免被迫选一种情绪。

现有 FastVLM 适配器强制从 engaged/confused/frustrated/bored/tired/sad 中选词；首 token 相对分数不等于校准置信度，关键词回退也不能证明准确。升级时优先问可观察事实（是否看向书、是否拿着手机、手在哪里），并保留 unknown。主观的“不想学习”优先采用用户自述。

## 4. 两种输入是来源，不应被混成同一种事实

```text
直接感知：脸/手/光线/可见物体 ──→ 带时间和质量的观察 ─┐
Margin：会话/题目/笔迹/对错/考试 ─→ 带任务标识的事件 ─┼→ 世界状态与历史
用户：手势/暂停/拒绝/偏好 ─────→ 明确指令 ─────────┘
                                                      ↓
                                     行为仲裁：该不该介入、介入到哪一级
                                                      ↓
                    照明控制 / 功能运动目标 / 表达方式 / Margin 消息请求
                                                      ↓
                          约束与中断 → 在线轨迹 → 模拟或实体执行器
                                                      ↓
                                 回看行为结果、日志和用户反馈
```

建议世界状态拆为：场景模式、学习行为、环境照明、手部交互、设备执行状态、用户偏好。手部控制与照明控制不必先把用户归类成某种情绪才工作。

新增事件应包含：`id, source, observed_at, received_at, ttl, quality, task_id, payload`。已有格式只覆盖部分字段；当前 app.stuck 等信号缺少完备的任务作用域与过期机制，需要升级，防止上一道题的“卡住”污染下一道题。消息重连需要序号、去重、确认和全量状态同步。

仲裁顺序建议：执行约束/停机 > 当前模式许可 > 明确的手动指令 > 工作照明与明确任务 > 证据充分的主动帮助 > 装饰性表达。

例如：摄像头发现皱眉、Margin 报告仍在持续书写，应继续等待；不能仅凭皱眉打断。用户拒绝提示后，暂停干预，不把其拒绝误写成识别失败。

## 5. 光线感知与冷暖光

目标是维持合适的工作区照明，而不是让灯光追着画面平均灰度变化。

第一步：实验室显示画面相对亮度，只用于观察亮暗变化。Mac 自动曝光、自动白平衡、屏幕反光都会影响结果，不能宣称测得 lux 或 Kelvin。

第二步：独立照度/颜色传感器，或经过曝光锁定与标定的视觉测量，选择桌面工作区并区分环境光、灯自身贡献、阴影和直射。目标照度与色温先作为用户可调产品参数，不编造适合所有人的唯一值。

第三步：低频闭环控制。误差＝目标照度−测得工作区照度，带死区、平滑、最大变化率、输出饱和与防积分累积。持续足够亮才缓慢调低或关灯；突然遮挡或镜头转动不能触发剧烈开关，避免灯改变画面又反过来调自己的振荡。

色温由用户偏好、会话任务、一天中的时段和可靠的环境测量共同给出目标，再缓慢过渡。环境变暗不自动等于应该变暖。手动调光建立一段可见的覆盖期，自动控制不能立刻把用户设置改回去。

验收：外部照度参考与输出曲线、亮暗阶跃响应、无闪烁、手动优先、失去测量时保持稳定。当前尚未完成。

## 6. 用户已明确的两种手势

### A. 桌面调光

用户确认：在桌面向上滑调亮、向下滑调暗。

桌面标定 → 检测手进入指定控制区 → 明确进入控制状态（短暂停留等可见反馈）→ 在桌面坐标系累计滑动位移 → 调整亮度 → 手离开则结束。不能把写字、翻页、拿杯子当调光。采用分段增量、死区、去抖和每次滑动冷却；具体阈值放配置。

### B. 灯头附近的空间引导

用户描述：手靠近灯头时灯头退让，手向前引导时灯头跟随；灯头朝向变化时，仍需保持直观的相对关系。

采用“相对位置/距离＋明确控制状态”，不直接把摄像头图像的 y 轴映射为灯头升降。用户对上下方向的括号描述有笔误，固定的绝对升降映射仍应在校准演示后确认。

候选实现：手掌进入近灯头区域并稳定 → 建立虚拟操作点 → 沿接近方向维持舒适间距、遇到靠近则退让 → 在可达范围跟随被引导的目标 → 手消失、越界或退出时减速停住。该设计是我们提出的实时控制方案，不能声称是论文公开的具体控制律。

单目手部关键点不能自动给出可靠的绝对距离；先用固定机位+桌面标定验证平面控制，再用深度/双目/近距测距补近灯头距离。灯头内摄像头会随灯运动，必须把图像坐标变换到桌面坐标；否则灯一动就可能把自己的运动误判为手在动。

另一个结构限制：头部摄像头低头看手/桌面时可能看不到脸。首轮 Mac 台架用人脸与桌面两个机位，或验证广角机位能否同时覆盖；实体阶段再决定摄像头数量和位置，不能承诺一个前置摄像头完整覆盖所有输入。

## 7. 学习场景的具体融合

| 场景 | 输入与判断 | 计划响应 | 当前缺口 |
|---|---|---|---|
| 开始学习 | Margin 会话开始＋人在场 | 一次短问候，转向工作区，稳定照明后减少动作 | 真正开始学习应以会话为依据；当前见到脸会自动进入 studying，需拆分“人在场”与“学习中” |
| 我不想学习 | 优先用户自述/暂停，其次只是疑似线索 | 提供休息或小目标选择；拒绝后安静 | 尚无正式 reluctance 指令；人工标注只记录，不影响策略 |
| 更新学习行为 | 题目标识、笔画、擦除、停顿、答题结果＋短期历史 | 持续有进展就不介入；恢复书写后撤销提示 | 实际 Margin 上报、消息时效、任务切换 |
| 不会做的区域 | Margin 区域坐标＋持续停顿/反复擦除；排除考试/拒绝 | 等待→看向该区域→征询是否需要提示→Margin 显示小提示；恢复书写则收回 | 接受/拒绝反馈协议、屏幕空间标定、真实提示 UI |
| 答对 | 明确 app.correct | 幅度有限的点头/短庆祝；灯光保持可用 | 已有动作与界面触发；未证明长期体验收益 |
| 答错 | 明确 app.wrong，结合连续错误次数 | 一次温和关注/等待，避免每错一次都责备式摇头 | 目前只有简单 hmm；需重设计连续错误的语义 |
| 严格考试 | 明确 app.exam，优先于推断 | 不给答案、不请求提示、不主动运动；保持照明 | 当前已经冻结运动；光照闭环与监测策略待补 |
| 自主备考防分心 | 用户启用专注模式＋可靠手机/拿取证据＋持续时间 | 低强度提醒、可取消；不给题目提示 | 手机检测未接入；应与严格考试分开配置 |

“防止拿手机”在本项目中指减少分心和自愿提醒，不代表灯能物理阻止拿取。严格考试目前不允许主动运动；不能因为推断出手机就绕过这条约束。

## 8. 按验证价值排序的升级

1. **本次：可观察性。** 左灯右摄像头，原始观测、规则分数、动作、规划结果、消息来源与自我标注。能指出每一次误判发生在哪层。
2. **直接操控。** 桌面调光、灯头近距引导先分别测；统一手动覆盖、丢跟踪停止与校准。并行接入照度测量，验证照明闭环。
3. **真实任务。** Margin 增加 session/task/笔迹/对错/区域/模式事件，完成一个真实“卡住→征询→提示→恢复书写”的闭环。
4. **连续动作。** 给定移动目标实时重规划，引入场景几何、可达性、接近人体/屏幕约束。实体不可执行的 hop/squash 从硬件动作集中剔除。用 MuJoCo 验证机构与执行限制，不能只看动画顺眼。
5. **语义与个性化。** 先对照有无 VLM 的增益，再决定是否承担其延迟与错误；最后优化等待时长/表达程度，不提前用自我强化的猜测训练策略。

申请材料的核心证据应是：主动帮助在什么时刻发生、何时选择保持安静、为什么、用户是否认可，以及同一任务下静态灯/表达灯的差异。

## 9. 怎样测试“我的几种情绪”

先分两种实验：表情动作可测性（转头、眨眼、微笑、眉部变化）与学习状态有效性（真实困惑、疲劳、自述不想学习）。刻意摆表情只能验证数值会不会变化，不能据此宣称识别了真实情绪。

逐段记录平静基线、一个变化、恢复基线；状态由你自报标注，标注不能回流给同一轮检测器。测试不同光线、角度、眼镜/遮挡、任务行为。看误报率、漏报率、延迟、每小时干预次数和被拒绝次数；把未知单列。当前 lab 提供标注和日志入口，尚无准确率报告。
